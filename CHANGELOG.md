# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [Unreleased]

### Added
- **A process log: every command says what it is doing, phase by phase.** Everything before the upload was silent — enumerating a large tree, dialing and authenticating, creating remote directories and, since the stat/hash work, comparing — which on a large artifact meant minutes of nothing on screen, indistinguishable from a hang. Commands now print one chronological stream where phases carry a `▸` and files their own marker: `scan`, `connect`, `compare`, `upload`, then the actions, each with the detail it produced (`13 file(s) · 275.4 MB · 1 excluded`, `stat 13 · cache 10 · hash 3`) and its duration. The names are shared across transfer commands so the same work reads the same way everywhere. A running phase rewrites its own line, so a long `compare` reports `hashing 2/13` as it advances; to make that movement real the remote batch size is now adaptive — 10 paths while there are few, 50 up to five hundred, 200 beyond that, where the round trip costs more than the work it reports on. Two live panes were rejected: they split the terminal height, have no headless equivalent, and a pipeline wants one ordered stream anyway. Headless and under `--json` the same stream becomes `[push] phase: detail` lines on stderr, and the result object gains `phases` with each duration in seconds, so a slow CI step is attributable. New persistent `-q`/`--quiet` leaves only the result and errors — a failed phase is still named, because a silenced command must say where it died. `-v` now also switches the phases to one line each, since a rewriting line cannot share the terminal with log output; for the same reason the `Connecting` info line became a debug one, its job now done by the `connect` phase. New `tui.StepLog`, the `ActionSink` shape applied to phases. This commit wires `push`; the other transfer commands follow.
- **`push` can leave paths out, and `teleport exclude` manages the list per project.** `push .` uploaded the entire `.git` directory — thousands of loose objects nobody wants on a server — and the only way to avoid it was naming every sibling by hand, since `push` deliberately does not read `.gitignore`. Three sources now feed one exclude set: the built-in default (`.git`), a per-project list in the local config (`push_exclude` in `~/.config/teleport/projects/<hash>.toml`, so it follows the working directory like the sync profile), and the repeatable `-x`/`--exclude` flag for one run. Patterns are `path.Match` globs resolved two ways: without a slash a pattern matches a **base name at any depth** (`-x node_modules`, `-x '*.log'`), with a slash it matches the **local path as you named it**, which is also how push prints it (`-x 'base/*.deb'`). A matching directory is pruned rather than filtered, so excluding `.git` costs one check instead of enumerating its contents, and filtering happens during enumeration so `--dry-run`, the byte total and the remote hash probe all agree. Naming an excluded path directly is a loud error instead of a run that uploads nothing. `--no-exclude` drops all three sources, `.git` included, for the rare push that wants them. The new `teleport exclude` command mirrors `teleport actions`: bare it opens a browser over the project tree where any entry at **any depth** can be toggled (`→` enters a folder, `←` goes up, `tab` marks, `enter` saves) — the directory worth excluding is usually nested, like `web/node_modules` or `base/logs`, and the existing local browser could not serve since it is single-select and uses `enter`/`tab` to descend. A nested pick is stored anchored to that one place, a top-level pick as a bare name that matches anywhere. The save only rewrites patterns the browser actually displayed, so a glob like `*.log` or an entry inside a folder you never opened survives. Plus `list` (shows each pattern's origin, honors `--json`), `add` and `remove`. A malformed glob is rejected when it is added and when it is used, rather than silently matching nothing. `push --json` gains `excluded`.
- **`teleport push <path>... [profile]` — a git-agnostic transfer for the files git hides.** Until now nothing could send a **gitignored** path: `sync -u` enumerates with `git ls-files --others --exclude-standard`, so an ignored path was skipped **in silence** while the command still reported success and the remote kept the stale copy; `beam`/`mirror` only carry what git has; and `ship` rejects anything that isn't an ELF/Mach-O/PE executable. Deploying a build directory therefore meant leaving teleport for a hand-written `scp`. `push` uploads the paths you name exactly as given, without reading the index or `.gitignore`: `teleport push web/dist`. The profile stays the boundary — `--to` is resolved relative to the profile's remote `path`, absolute values are rejected, and any destination that would escape the profile directory via `..` is refused, so `push` can never write elsewhere on the box. With a single path `--to` is the exact destination (`push web/dist --to web/dist.new` renames the tree); with several it is a parent directory. Directories are recursive and every directory in the tree (empty ones included) is created remotely; symlinks are followed and their content uploaded, while a broken symlink or a symlink cycle is a loud error that aborts *before* anything uploads. Only the execution bit is preserved (`0755`/`0644` — no unconditional `chmod +x`, that stays `ship`'s job). Every upload is size-verified, and `--checksum` adds a SHA256 comparison on both ends. `--dry-run` prints the full plan without opening a connection, and the repeatable `--then`/`-t` runs actions after a successful transfer over the same connection — which is the clean-replace recipe, since there is deliberately **no** rsync-style `--delete` in v1: `teleport push dist --to dist.new --then swap`. Honors `--json` (`{command,target,sent,bytes,verified,files[],actions[]}`) and the exit-code contract. New `ssh.Client.MkdirAll`/`Chmod`. `sync`'s semantics are unchanged — it remains the git-aware command, and `push` is the explicit escape hatch.
- **`teleport --sh` shortcut for `teleport shell`.** A root-level boolean flag that dispatches to the existing interactive-shell command (Unit 16), so opening a remote shell no longer needs the full subcommand: `teleport --sh` uses the working directory's default profile and `teleport --sh <profile>` a named one. The remote shell stays `zsh`; this is only sugar over `teleport shell`, following the same root-dispatch pattern as `--sync`/`--init`/`--profiles`/`--beam`. It is `--sh` (long flag, no shorthand) rather than a single-dash `-sh` because cobra shorthands are one letter and `-s` is already `--sync` (so `-sh` would parse as sync + help).
- **The remote directory browser can create the destination folder named after the local project.** In `teleport init`'s sync and bin directory pickers, `ctrl+n` creates a remote subfolder named exactly like the local project directory (`basename` of the cwd) inside the folder currently shown, then descends into it so `enter` confirms it — no more pre-creating the remote folder over SSH by hand to mirror the project name. The key is idempotent (an existing folder is entered, not re-created or errored) and only appears when a project name is available, so unrelated dir pickers (e.g. `teleport actions add`) are unaffected. New `ssh.Client.Mkdir` (idempotent remote `mkdir`).

### Changed
- **`teleport beam` reports its phases, and says what it sent.** Resolving the commits ahead, reading the files out of them and connecting were all silent, which on a branch with dozens of commits is several seconds of nothing before the picker appears. It now prints `scan` (commits ahead of the branch), `collect` (files read out of the selection), `connect`, `upload` and, when the selection deletes files, `delete` — then a closing `✓ beamed N file(s) from M commit(s) → host:/path` with how many were removed and the elapsed time, where the run used to just end. `--json` gains `phases`. The per-file `removed` info line became a debug one: the `delete` phase states the count, and an info line per file would land inside the live phase line.
- **`teleport sync` reports its phases, and says what it did when it finishes.** It shared push's silence: the git enumeration and the connection happened with nothing on screen, and the run ended on the progress view without a summary — a sync of 40 files left you counting lines to know it worked. It now prints `scan` (with the file count and how many untracked files were left out, which used to be a warning buried after the upload), `connect` and `upload`, then a closing `✓ synced N file(s) → host:/path` with the elapsed time. `--json` gains `phases`. The `upload` phase keeps its real duration while the transfer view owns the screen, via a new `StepLog.Detach` that closes the live line but leaves the phase running.
- **`teleport push` decides what to skip from metadata, not by hashing everything.** Comparing both ends with SHA256 cost no bandwidth but plenty of work: every run read each local file in full and had the server read its copy in full, including files whose size already proved they differed. Each run now asks the cheapest question that can settle a file. A batched remote `stat` comes first (new `ssh.Client.RemoteStatMany`, one command per 200 paths, running the GNU and BSD spellings back to back so the flavor the server has answers): missing remotely or a different size means upload, with nothing hashed. Then a local cache keyed by remote path — `~/.config/teleport/cache/<project>-<profile>.json`, kept out of the project config because every command reads that file — holds the hash of destinations already proven identical along with the size and mtime of **both** ends at that moment; while all four still match, the file is skipped without reading a byte, and an edit made on the server invalidates the entry just as a local one does. Only the remainder is hashed, as before. A second push of an unchanged tree now costs a single `stat` command, and a large unchanged artifact is neither resent nor re-read on either machine. The `(size, mtime)` heuristic is git's, with git's blind spot — a file rewritten in place keeping both — so `--checksum` now also means "hash instead of trusting the cache", on top of its post-upload verification; `-f` still forces the upload itself. The cache is disposable: deleting it, or a corrupt file, costs one round of hashing and never a wrong decision. `-v` now reports `size differs` and `cache hit` alongside the existing reasons.
- **`teleport push` only sends what the remote does not already have.** A second push re-uploaded every byte it had just uploaded: nothing compared the two ends, so refreshing one file inside a build directory meant resending the whole tree, and a large artifact that never changes (an archive, a media file, a compiled bundle) was retransmitted on every run. Before uploading, push now computes the SHA256 of each destination **on the server** — one batched `sha256sum`/`shasum` command per 200 paths, so only the digests cross the network, never the remote contents — and compares it against the local file; identical files are skipped. Pushing an unchanged tree now costs no bandwidth and the progress view lists only what is actually sent, above a `↷` line per skipped file so a short run is never a mystery. `-v` logs the reason each file is being sent — missing remotely, or the two hashes that disagree. `-f`/`--force` skips the comparison and uploads everything, which is the way to repair a remote file whose content is wrong in a way the hash agrees with (a bad mode, a half-applied manual edit). Files missing remotely, or whose local copy cannot be hashed, always upload. `--json` gains `skipped` and a per-file `skipped` flag, and `bytes` now counts what was transferred rather than what was enumerated; `--dry-run` still connects to nothing, so it lists the full plan and the real run is what skips. New `ssh.Client.RemoteSHA256Many`.
- **`teleport ship` bin profiles are now per-project.** Previously a bin profile (host, remote `bin/` path, optional `remote_name` and `bin_file`) lived in the **global** config keyed only by target OS, so a machine could hold exactly one ship destination per OS across *all* repositories — the CLI's per-directory project model didn't reach `ship`. Bin profiles now live in the project's local config (`~/.config/teleport/projects/<hash>.toml`) under `[bin_profiles.<os>]`, so different repos can ship different binaries to different servers without interfering. `teleport init` writes them there, and `teleport profiles`/`teleport config get` display the project's own set. The global `[bin_profiles]` section is **deprecated**: it is no longer consulted for resolution, and the first interactive `ship`/`init` in a project without its own bin profiles offers to adopt the global entries (and optionally clear the global section). Non-interactive runs never prompt — they warn once and leave the deprecated section unused.

### Fixed
- **`teleport shell` / `teleport --sh` no longer fails on a server without `zsh`.** The remote command was the fixed `cd <path> && exec zsh`, so on a box where `zsh` is not installed the session died immediately with `zsh: command not found` and exit `127` — the shortcut was unusable on any default Debian/Ubuntu/Alpine server, and the only way in was a hand-typed `ssh`. The remote shell is now resolved on the box: `zsh`, then `bash`, then `sh`, taking the first that exists. Each candidate is probed with `command -v` before being `exec`'d, because a failed `exec` replaces and kills the login shell instead of falling through to the next candidate. If none of the three exists the command reports `teleport: no shell found on the remote (tried zsh, bash, sh)` on stderr and exits `127`, and a `cd` into the profile path that fails still aborts before any shell is started. Everything else is unchanged: it is still `ssh -t` and still `syscall.Exec`, so the session is indistinguishable from a hand-typed `ssh`.
- **`teleport actions add` can finally create an action headless.** The headless path took the action's name only from `actions edit <name>`, so on the `add` route it always arrived empty and the command aborted with `exit 2` no matter how many flags were passed — actions could only ever be created through the interactive wizard, and `edit` was no alternative since it requires the action to already exist. New `--name` flag on `actions add` supplies it: `teleport actions add <profile> --no-input --name doctor --run "uname -m" --run "df -h ."`. The name is validated with the wizard's own rules (non-empty, no spaces), and the misleading error that blamed a missing `--run` now names the flag that is actually missing. A flag rather than a positional keeps the existing `add [profile]` signature (where the first positional is the profile) working. The permission model is untouched: an action stored with `--confirm` still refuses to run headless without `-y`.
- **`teleport ship` no longer leaks one project's bin profile into every other repo.** Because the old global `bin_file` matched for any working directory, running `teleport ship` in an unrelated project would try to stat that other project's `bin_file` (failing, or shipping the wrong file), and the global `remote_name` would silently rename an explicitly-passed binary — overwriting a different project's remote binary via `mv -f`. With bin profiles scoped per project, resolution only ever sees the current repo's configuration.

## [0.9.0] - 2026-07-22

### Added
- **`teleport mirror` — a git-faithful deploy that advances the remote branch to your local commits with identical hash and message.** Unlike `beam` (which copies file *contents* over SFTP and leaves the remote working tree dirty without touching git history), `mirror` transfers the actual git *objects* via `git bundle`, so the remote's `git log` matches yours exactly and its working tree ends clean at the new HEAD. Because the objects are transferred verbatim, the hash and commit message are preserved by construction (no re-committing). The picker is single-select — you choose *how far to advance* (`remoteHEAD..chosen`); the reflected range is always a contiguous prefix from the remote HEAD, which is what guarantees the hash. `-a`/`--auto` advances to HEAD without the picker (required in headless, per the `--no-input` rules); `-c`/`--clean` chains `clean` first for a dirty remote; `-f`/`--force` allows a non-fast-forward `reset --hard` behind a confirmation (headless requires `-y`/`--no-input`); a fresh/unborn remote repo is bootstrapped with a full bundle. Honors `--json` (`{command,target,branch,from,to,commits[],fast_forward,forced}`) and the exit-code contract. No new config or state — the remote HEAD itself is the source of truth. New git helpers `RevParse`/`IsAncestor`/`MergeBase`/`CommitsBetween`/`BundleTo` and a single-select target picker.
- **Headless mode via a persistent `--no-input` flag.** Any command can now run without a TTY: `--no-input` (or simply not having a terminal on stdin, as in CI or when another process launches `teleport`) turns every prompt, picker, and viewer into a non-interactive path that either resolves from flags or **fails closed** with exit code `2` and a message naming the flag that was missing — it never hangs waiting for input. A single `interactive()` guard (real TTY on stdin *and* no `--no-input`) governs all TUI call sites. `teleport beam -a --no-input` sends the unsent commits end to end without opening the commit picker or the file-diff viewer; `teleport clean --no-input` implies `-y` (headless never discards without an explicit confirmation, so `clean` with no TTY and no `-y`/`--no-input` exits `2` and leaves the remote untouched); and, by design, `--no-input` does **not** silently imply `-a` for `beam` — headless without `-a` is an explicit error so unintended commits are never beamed. In a real terminal with no flags, `beam`/`clean` behave exactly as before.
- **Machine-readable output via a persistent `--json` flag.** With `--json`, each command prints a single JSON result object to `stdout` and sends all decoration/progress to `stderr`, so callers parse instead of scraping ANSI. `status` emits `{target, in_sync, total, drift[]}` (with `state` ∈ `differ`/`missing_remote`/`missing_local`); `sync`/`beam` emit `{command, target, sent, files[]}` (`beam` also lists the `commits[]`); `clean` emits `{command, target, reverted, removed, restored, removed_ignored}`; `pull` emits `{command, target, pulled, files[]}`. A headless `ErrNeedsTTY` under `--json` is serialized as `{"error":…,"hint":…}` on `stderr` with exit `2`.
- **Documented, stable exit codes:** `0` success / in sync, `1` execution error or drift detected (`status`), `2` a selection or confirmation could not be resolved from flags without a TTY.

- **`teleport mirror`'s target picker can now preview a commit's changes.** With the cursor on a commit, `d` opens that commit's full diff (`git show`) in a bat/delta-style scrollable pager — multi-file, each file under its own header bar with per-file syntax highlighting and `+adds −dels` in the header. `esc`/`q` returns to the picker with the cursor intact; `enter` still confirms the target. Read-only and orthogonal to selection, mirroring beam's `d`. New `git.CommitDiff`, `highlight.CommitDiff`, and a `commitDiffViewer` sub-model; the git+highlight I/O lives in a loader closure in `cmd/mirror.go` (architecture invariant #3).
- **Commit tags are colored by type in the pickers.** The commit picker and the mirror target picker parse the `[TAG]` prefix of each commit subject and render it as a bold, semantically-colored chip (`[ADD]` green, `[FIX]` red, `[DOC]` blue, `[REF]`/`[IMP]` purple, `[MERGE]` cyan, `[REL]` gold; unknown/none stays neutral), so a list of commits reads by type at a glance (`theme.TagChip`).
- **Actions — named remote command sequences per profile, with live log streaming.** An action (`deploy`, `restart`, `logs`, …) is an ordered list of commands stored under `[profiles.<name>.actions.<action>]` in the global config: `run` (the steps), optional `cwd` (defaults to the profile path; `""` means no `cd`, so `systemctl`-style commands work), optional per-step `timeout` (default 10m), and optional `confirm`. Actions run over the profile's SSH host and are **not tied to the profile's directory**. `teleport run <action>... [profile]` runs them standalone (`--list` shows them), and `sync`/`beam`/`mirror` gain a repeatable `--then`/`-t` flag that chains actions after a **successful** transfer over the same connection. Each step's stdout/stderr is **streamed back line by line** via a new `ssh.Client.RunCommandStream` (no PTY, so output stays clean) and rendered by `internal/tui.ActionSink` — colored to stdout interactively, or `[name]`-prefixed lines to stderr headless so `--json` keeps stdout a clean object with the per-action results nested under `actions`. The first non-zero step aborts the action and the chain (exit `1`); `--then` names are validated before the transfer starts; and an action with `confirm = true` prompts interactively but needs `-y`/`--no-input` headless (else exit `2`). Manage actions interactively with `teleport actions add/list/edit/remove` — the `add`/`edit` wizard captures name → steps → working directory (via the remote dir browser) → options, and offers "test now, then save" that runs the action with live streaming before persisting.
- **`teleport beam` can now select explicit commits headless via a repeatable `--commit`/`-C` flag.** Previously the only non-interactive selection was `-a` (all unsent commits) — there was no way to say "send exactly these" from a script. `--commit <sha>` accepts a short SHA, full SHA, or ref (`HEAD~2`), resolved via `git rev-parse`; each must be among the commits ahead of the remote (an out-of-range commit fails with exit `1`, naming the rejected SHA and listing the valid ones, before connecting). Non-contiguous subsets are allowed (beam is file-level), duplicates are deduped, and the send order follows the branch's topological order — not the flag order — so uploads read the same as the picker's. Selection is imperative: it re-sends even a commit already marked sent, and updates the tracking on success. `--commit` and `-a` are mutually exclusive, and `--commit` also works interactively (it skips the picker but still opens the file-diff viewer under a TTY). This makes `beam` fully operable from CI: `teleport beam --commit a1b2c3d --commit e4f5a6b --no-input --json`.

### Changed
- **Unified the color palette behind a single `internal/theme` package.** Every `cmd/` and `internal/tui/` style now references a semantic token (`Accent`, `Success`, `Warn`, `Danger`, `Header*`, `Icon`, `Text*`, `Hint`, …) instead of hardcoding `lipgloss.Color("NN")` — no raw color literal survives outside `internal/theme` (except `internal/highlight`, chroma's domain). This collapses the drift that had crept in: the upload-fail `✗` now uses the same red (`Danger`) as delete/status/pull instead of a second one, the five ad-hoc greys are down to a named ramp, and the mirror/branch pickers gain the same pink cursor the commit/dir pickers already had. The beam per-commit palette is unchanged in look and purpose — just relocated to `theme.CommitPalette`.

### Documentation
- README: documented the new `teleport mirror` command — a "Mirror" section explaining the git-object transfer and the same-hash guarantee, a `beam` vs `mirror` comparison table, the new command in the commands table and the "Three ways to ship code" intro, and a "Scripting (headless)" section covering the `--no-input`/`--json` flags and exit codes. Added a simulated `mirror` demo GIF (new `_sim_mirror` in `demo/sim/teleport-sim.sh` + `demo/tapes/mirror.tape`), embedded inline and in the command gallery.

## [0.8.0] - 2026-06-30

### Added
- The `teleport beam` file/diff viewer can now page between files without returning to the picker: inside the viewer `←`/`→` (aliases `n`/`p`) jump to the previous/next file, wrapping at the ends. The current mode is kept across the jump, so paging through a commit shows each file's diff (or each file's contents) in sequence instead of forcing an `esc` → move cursor → re-open round-trip per file. Navigation respects the active commit filter — it steps through exactly the files the picker is showing — and the viewer footer gains a `←/→=file N/M` position indicator (shown only when the range holds more than one file).

### Fixed
- The `teleport beam` file picker's commit count no longer silently undercounts. When several selected commits rework the same files, `git.FilesInCommits` dedupes each path to the newest commit that touched it, so older commits that own no surviving file used to vanish from the count line — selecting 5 commits could read "3 commits" with no explanation, even though all 5 are still beamed and credited as sent. The picker now tracks the selected-commit total separately from the contributing commits and surfaces the gap explicitly: it reads `5 commits · 3 with files` when they differ, and the plain `5 commits` when every selected commit owns a file. The filter-by-commit (`←/→`) still steps only through commits that have visible files.

## [0.7.0] - 2026-06-29

### Added
- The `teleport beam` file picker can now preview a file before sending it: with the cursor on a file, `v` opens the full file (the blob at that file's commit) and `d` opens the diff that commit introduced — both in a `bat`-style pager with syntax highlighting and a line-number gutter. Inside the viewer `tab` switches file ⇄ diff, scroll is `j/k`/`↑↓`/`ctrl+d`/`ctrl+u`/`g`/`G`, and `esc`/`q` returns to the picker with the cursor and selection intact. Viewing is orthogonal to selection — it never changes what gets beamed. Deleted files show their pre-delete contents in file mode and the deletion hunk in diff mode; binary blobs show a placeholder. Highlighting is done by a new `internal/highlight` package wrapping chroma (pure Go, no CGO), with the Catppuccin-Mocha style.
- The diff view is rendered **delta-style**: the code on each line is syntax-highlighted, with a tinted two-column (old/new) line-number gutter marking added (green), removed (red), and context (dim) lines. Each hunk opens with a full-width bar separating the `@@` line range (dim) from the enclosing function/class context (accent), with a blank line between hunks. The redundant unified-diff file header (`diff --git`/`index`/`---`/`+++`) is hidden — the viewer header already shows the path and commit.

## [0.6.0] - 2026-06-29

### Added
- The `teleport beam` commit picker now lets you manually mark/unmark commits as "already beamed" without re-sending: `m` toggles the sent badge of the commit under the cursor (live), and `M` toggles all commits at once (symmetric — marks all, or unmarks all if every commit is already marked). This corrects the sent-tracking for commits that are genuinely on the remote but show as pending because identity is the exact SHA (new branches with no history, rebased/amended/cherry-picked commits, or the first beam from another machine). Marks accumulate during the picker session and are persisted to the per-profile beamed store only on `enter` (the write happens as soon as the picker confirms, so marks survive even if the file picker or upload is later cancelled); `ctrl+c` discards them. The delta (added + removed SHAs) is applied in a single atomic write via the new `LocalConfig.ApplyBeamedDelta`, and removals are scoped to the commits actually shown so stale SHAs in history are never disturbed. `beam --auto` skips the picker, so manual marking is inert there by design.

### Documentation
- Added animated demo GIFs for every command and embedded them in the README: a hero GIF (`profiles` → `sync`), inline GIFs in the `beam`/`ship`/`shell` sections, and a collapsible "Every command in action" gallery (`init`, `sync`, `status`, `clean`, `pull`, `profiles`, `config`, `version`/`--help`). The GIFs are recorded with [VHS](https://github.com/charmbracelet/vhs) and are fully simulated: a `teleport()` shell function under `demo/sim/` renders each command's real styled output — colors and Nerd Font glyphs extracted byte-for-byte from the Go source via `gen-glyphs.sh` — using invented data only (no network, no real config, no private paths). The demo tooling lives in `demo/` (`sim/`, `tapes/`, `gifs/`) with `demo/README.md` documenting how to regenerate the GIFs with `vhs`.

## [0.5.0] - 2026-06-17

### Added
- `teleport shell [profile]` — opens an interactive shell on the remote, already `cd`'d into the profile's remote path. It derives the host and path from the existing sync profile (no extra configuration) and runs `ssh -t <host> "cd '<path>' && exec zsh"`. The command replaces its own process with the system `ssh` binary (`syscall.Exec`), so it behaves exactly like a hand-typed `ssh` — native TTY, colors, agent, `~/.ssh/config` — and leaves no teleport process running while the session is open. The existing `sync`/`beam`/`ship`/`clean`/`pull` commands are unaffected; the new code is isolated to `cmd/shell.go` (with a `syscall.Exec` Unix path and an `exec.Command` Windows fallback).

## [0.4.0] - 2026-06-11

### Added
- `teleport beam` gained an `--auto`/`-a` flag that skips the commit picker entirely: it auto-selects exactly the commits not yet beamed to the active profile (the same set the picker pre-selects) and goes straight to the file review. When every local commit ahead of the remote was already sent, it prints `Nothing to beam — all local commits on <branch> already sent.` and exits.
- New root-level shortcut `teleport -b`/`--beam` runs the beam flow without typing the `beam` subcommand, matching the existing `-s`/`-i`/`-p` shortcuts. It combines with the auto shortcut as `teleport -ba` (a root-level `-a`/`--auto` flag bound to the same behavior). The full `teleport beam` subcommand remains the only way to pass beam's own sub-flags (`--branch`, `--clean`, `--then-sync`, `--yes`).

### Changed
- The beam send/progress view is now grouped by commit instead of a flat file list. Each commit gets a colored header (`󰆧 [shortSHA] ─ subject`) using the same per-commit accent as the file picker, with its files listed underneath marked `✓` uploaded / `✗` failed / `·` pending. ## [0.2.0] - 2026-06-02

### Added
- `teleport ship [bin]` — deploys a locally built CLI binary to a remote `bin/` directory in three automated steps: SFTP upload to a `/tmp` staging path → `chmod +x` → `mv` into the target dir (with automatic `sudo` escalation when the SSH user cannot write the destination). Target OS is auto-detected from magic bytes (ELF→linux, Mach-O incl. fat binary→macos, MZ/PE→windows); `--os` overrides detection. `--to` overrides the configured `bin_path` for the current run only. `--name` renames the binary on the remote. When `sudo` is needed, `sudo -n` is tried first; if a password is required a masked `huh` prompt appears, and on cancellation the binary is left under the staging path with a message pointing there. New `internal/bindetect` package handles magic-byte sniffing.
- `bin-dir` local config key (`teleport config set bin-dir ./bin`) — stores the project-local directory where built binaries live. `teleport ship` without an argument reads this key: auto-selects the only file if there is one, or opens a `huh.Select` picker when multiple files are present. Configured interactively in `teleport init`.
- `teleport init` now opens a multi-select at the start so the user can configure any combination of: sync profile, bin profile for Linux, bin profile for macOS, bin profile for Windows. Sync and bin flows are independent and can both be configured in a single session. A final step asks for the local `bin-dir` (autodetects `./bin` if it exists). Bin profiles are stored in `[bin_profiles.<os>]` in the global config; `teleport config set bin-dir` persists the source dir in the local project config.
- `teleport profiles` now prints two labeled sections — `Sync profiles` and `Bin profiles` — omitting either when empty.
- Remote directory browser now shows hidden directories (e.g. `.local`, `.config`) alongside visible ones, enabling navigation to paths like `~/.local/bin`.

### Improved
- `teleport init` remote directory picker accepts a custom header per invocation (`RunDirPickerWith`), so sync and bin flows show contextual titles instead of a generic "Remote Directory Browser".
- `teleport init` bin profile setup now asks for an optional `remote_name` (fixed filename on the remote) and `bin_file` (local binary path, auto-detected from `./bin/<os>` patterns). Tab no longer accidentally submits the multi-select — only Space/x toggle and Enter confirms.
- `teleport ship` resolves the local binary from `profile.bin_file` automatically when configured, skipping the picker on every run. Remote filename priority: `--name` flag > `profile.remote_name` > local basename. Ship prints all steps upfront (ANSI cursor movement updates each line in place — yellow spinner while active, green ✓ on success); the upload line shows a live `[===>   ]` progress bar sized to the terminal width (`TermWidth()` via `TIOCGWINSZ`) plus `X MB / Y MB  N%`. Nerd Font icons per step: `󱓞` header, `󰕒` upload, `󰑕` rename, `󰯄` chmod, `󰔰` move, `󰗠` shipped. When the remote name differs from the local filename, an explicit `renaming  original → remote` step appears between upload and chmod. Upload speed improved: SFTP uses `UseConcurrentWrites` + `sftp.File.ReadFrom` on the fast concurrent (pipelined) path instead of 32 KB sequential `io.Copy` writes.
- `teleport init` bin profile setup now uses a local filesystem TUI picker (navigable with ↑↓, Tab/→ to descend, ← to go up, Enter to select) for choosing the local binary file instead of a text input. The `bin-dir` question is skipped entirely when all configured bin profiles already have a `bin_file` set.

### Fixed
- `teleport ship` no longer leaves a 0-byte file on the remote while reporting success. The SFTP write packet was capped at 4 MiB (`MaxPacketUnchecked(1<<22)`), which exceeds OpenSSH's `SFTP_MAX_MSG_LENGTH` (256 KB) and made the server discard the payload; it is now `MaxPacket(32768)`. Upload functions (`UploadFile`, `UploadFileProgress`, `UploadBytes`) now close the remote handle explicitly and propagate its error (servers often only report write failures on close), and verify the remote size matches the local size before reporting success.
- SFTP uploads now actually use the concurrent (pipelined) path: `progressReader` exposes `Size() int64` so `sftp.File.ReadFrom` no longer falls back to the slow sequential per-ACK write loop.
- Password authentication is functional again: `ConnectWithPassword` used `MaxPacketChecked(1<<20)`, which `MaxPacketChecked` rejects (>32 KB) and caused `sftp.NewClient` to fail; switched to `MaxPacket(32768)`.
